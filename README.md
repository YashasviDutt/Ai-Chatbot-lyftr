## 2. Run locally
**With Docker** (needs Docker + make):
```bash
cp .env.example .env      # put at least 2 real keys in LLM_API_KEYS

```
**Without Docker**:
```bash
# backend
cd backend && pip install -r requirements.txt
export LLM_API_KEYS=key1,key2 DATABASE_URL=sqlite:///./app.db ENABLE_FAILURE_SIMULATION=true
uvicorn app.main:app --port 8000
# frontend
cd frontend && npm install && VITE_API_URL=http://localhost:8000 npm run dev   # :3000
# tests (no network or real keys needed)
cd backend && python -m pytest -q
```

## 3. Design decisions
**Key fallback.** `LLM_API_KEYS` is parsed into `key_1..key_N`. For every request `llm.complete()` calls `litellm.completion()` with `key_1`; on *any* exception (429, quota, 5xx, timeout, auth) it moves to the next key and counts the failure in `fallback_attempts`. If all keys fail the API returns `503 {"detail":"all providers unavailable"}` and nothing is written to history. Keys are never logged or returned, only their ids. The order is deterministic (always start at `key_1`), which keeps failover easy to demonstrate. A production version would add per-key cooldowns.

**Caching.** LiteLLM's built-in `Cache` in in-memory mode (`CACHE_TYPE=local`, the default). LiteLLM's cache key is built from the model and the full message list and does not include the API key, so a response generated by `key_2` is a hit for `key_1` too. A hit is detected via `_hidden_params["cache_hit"]`, and it reports `LLM_CACHE`, `key_id: null`, `fallback_attempts: 0` and the stored token usage. Because the cached messages are `system + history + new message`, the same first message in a new session hits the cache, while any different history or message misses. Requests carrying `X-Simulate-Failure` skip cache *reads*, so failover is always exercised. Trade-off: the in-memory cache is cleared on restart (history in SQLite is not). `CACHE_TYPE=disk` is supported only on LiteLLM versions that still ship the disk backend and otherwise falls back to in-memory.

**SQLite session storage.** `messages` table exactly as specified, plus a small `sessions` table for the per-session system prompt and an index on `(session_id, id)`. The schema is created on startup, the file lives on the `appdata` volume at `/data/app.db`, and WAL mode is on. The user and assistant rows are written in one transaction only after a successful reply, so failed requests (422/503) never pollute history.

**Failure simulation.** `X-Simulate-Failure` is parsed per request and only honored when `ENABLE_FAILURE_SIMULATION=true`. Listed keys raise a simulated error before any provider call, so it behaves like a real 429/5xx but costs no quota.

## 4. Verification
```bash
B=http://localhost:8000
curl $B/health
# live, then cache hit in a NEW session (same first message)
curl -s $B/chat -H 'Content-Type: application/json' -d '{"session_id":"a1","message":"What is the capital of France?"}'
curl -s $B/chat -H 'Content-Type: application/json' -d '{"session_id":"a2","message":"What is the capital of France?"}'   # LLM_CACHE, key_id null
# failover
curl -s $B/chat -H 'Content-Type: application/json' -H 'X-Simulate-Failure: key_1=429' -d '{"session_id":"a3","message":"Tell me a joke"}'   # key_id key_2
curl -si $B/chat -H 'Content-Type: application/json' -H 'X-Simulate-Failure: *=429' -d '{"session_id":"a4","message":"Hi"}'               # 503
# history + token usage
curl -s $B/sessions/a1/messages
```
In the UI, every reply shows source, model, latency and the per-request input/output tokens. "Session settings" has the system prompt and a "Simulate failure" field for the demo.

## Deployment notes
- **Backend** (Docker): needs a persistent volume mounted at `/data` (Fly.io volume, Railway volume, Render paid disk). Set `LLM_API_KEYS`, `DATABASE_URL=sqlite:////data/app.db`, `ALLOWED_ORIGINS=<frontend url>`, `ENABLE_FAILURE_SIMULATION=true`. The container honors `$PORT`.
- **Frontend**: Vercel/Netlify with root `frontend`, build `npm run build`, output `dist`, env `VITE_API_URL=<backend url>` (build-time).
